整理日期：2026-11-26。实施授权：2026-11-27，用户已要求按本计划更新，验收后只发布公测。下文保留规划阶段的原问题、要求和验收，当前实施结果以 `V0.0.20_TEST_REPORT.md` 为准。

本文汇总本轮全部需求、阅读结论和卡顿排查结果，供用户核对。每一项分别按“问题、要求、验收”编写。本文是计划，不是已经完成的更新或检测报告。

## 本轮范围与共同约束

- 规划阶段基于 v0.0.19，只做阅读和排查；现已获准实施 v0.0.20、构建、验收并发布公测，禁止同步正式库。
- v0.0.20 仅在公测库 `yydcm-129/Moyun:main` 上线，对应公测站 https://yydcm-129.github.io/Moyun/ 。用户已于 2026-11-27 授权验收后发布公测；正式库 `Not1a-del/Moyun:main` 和正式站不纳入本轮发布。
- 保持单页网页使用方式，不要求用户部署服务器、安装向量数据库或本地模型。开发源为 `Moyun/source/moyun.single.html`，发布文件由项目原构建流程生成。
- 本项目启用向量时使用用户配置的外部 embeddings API；外部重排也需要对应 API。基础关键词检索和规则排序可在浏览器本地完成。不得把额外 API 请求、费用或可用性依赖隐藏在普通浏览、输入和打开设置中。
- 保留旧书、正文、分支、角色资料、记忆、手工修改和备份的兼容性。自动总结、向量重建、外部重排与已有记忆的读取分开控制；保留旧书明确关闭的选项，不擅自开启付费维护。
- 创作数据继续归属书籍，通过 `DB.saveLibrary` 进入原 IndexedDB 路径。不得为新创作数据增加 localStorage 存储。第 5 项涉及的底层分记录方案须在开工前说明与现行存储规则的关系；若确实需要改变规则，先让用户核对具体范围。
- 实施时先保护原有未提交内容，再从确认的稳定基线建立备份或版本分支。代码尽量精简，复用公共保存、请求、选择和表单能力，不为每个入口重复实现一套逻辑。

## 1. 上下文预算、摘要质量与失效设置

### 问题

1. 当前前文预算主要扣减原文字数。章节摘要、逐章记忆、合并记忆、范围总结、卷末交接和增强召回可继续附加，最终发送量可能明显超过界面表达的上限。
2. 世界资料和角色资料中存在强制保留项超预算仍发送的行为。这与用户希望控制实际发送量的目标不符。
3. 章节摘要存在硬截到 120 字的保存路径。复杂章节的人物状态、物品归属、承诺、秘密和因果链容易在压缩时丢失；已被截掉的内容无法仅靠改大设置恢复。
4. “摘要章数”和“单章摘要上限”有界面与保存字段，但当前前文组装没有按它们组织结果，用户调节后看不到对应变化。
5. 记忆默认关闭、付费维护与读取的边界需要讲清楚。简单把所有开关默认打开会增加请求和费用，不能据此解决记忆质量。

### 要求

1. 统一统计最终请求中的正文、摘要、记忆、父块补充、召回、交接、世界资料、角色和固定提示词，区分“前文预算”“资料预算”与“总输入估算”。同一条信息去重后再计入，不能只统计原文。
2. 字符数与 token 估算分别显示；没有对应模型的精确分词器时标注估算，不把字数当作准确 token。为输出和推理预留空间，避免检索结果挤掉当前写作要求。
3. 作者明确钉选的事实、本章关键人物约束和近期承接优先于一般旧材料；普通候选超预算时按相关度舍弃。必带项本身超过上限时明确指出原因和条目，由用户调整上限或内容后发送，不继续静默超发，也不默默删掉必带内容。
4. 取消“长期记忆只能依赖 120 字摘要”的设计。保留章节卡简短摘要的用途，长期记忆从原文提取可追溯的事实和片段；生成摘要的目标长度与本次发送上限分开处理。不得为减小请求而改短用户已经保存的全文摘要。
5. 接通摘要章数、单章摘要上限、全文章数、前文总上限、省 token、范围总结与原文替换选项。明确每个选项控制哪一层；值为 0、关闭截断和旧设置升级都有一致行为，不在生成时改写用户的保存值。
6. 读取已有摘要或记忆不需要自动付费补录。缺少记忆、摘要过短、条目未发送时给出具体状态与手动补录入口；旧书付费维护开关保持原意。

### 验收

1. 使用同时含近期正文、长摘要、逐章记忆、父块、范围总结、卷末交接、强制设定和角色的样例，拦截最终请求，逐项核对实际内容、预算占用和未发送原因。不能只检查预览面板的数字。
2. 分别把摘要章数设为 0、1、10，摘要上限设为 100、500、3000，在有足够长原摘要的样例上证明请求随设置变化；保存、刷新、切书后行为一致，原摘要不被截短。
3. 组合验证全文章数为 0、省 token 开关、截断开关、记忆只读、自动总结关闭、原文替换开关；确认设置之间不会回写或绕过彼此。
4. 必带项超限时显示准确条目并阻止未经调整的超发；普通候选不足以全部容纳时，保留优先项，报告舍弃原因。
5. 对含关键承诺、人物关系变化、物品转移、秘密知情人与未解事件的章节核对事实保留情况，不能把摘要变长视为质量已达标。旧摘要的补录另行执行，不宣称已找回原来被截掉的文字。

## 2. 父子块、混合搜索、重排与外部 API

### 问题

1. 当前主要依赖逐章总结和固定五章合并，合并结果继续压成约数百字；原逐章记录虽保留，但更细的事实没有形成可按需读取的检索链路。
2. 已有合并记录不参与当前增强向量候选的同等检索，也没有完整的“小片段命中后补足原文上下文”过程。仅把摘要改名为父块不能解决问题。
3. 当前增强召回以向量相似度、固定阈值和条数为主。人物专名、物品、别名适合关键词命中，改写表达适合语义命中，单一渠道容易漏掉其中一类。
4. 本项目没有内置本地向量模型，启用向量需要外部 API。服务商是否支持 embeddings、批量输入、指定维度或重排不能由普通聊天接口可用来推断。

### 要求

1. 建立两层材料：子块按自然段、场景或明确事件保留细节；父块保留所属章节或相邻场景的较完整上下文。每块有稳定 ID、书籍、分支、章节、原文位置和版本信息。切块避免从句中截断，重叠范围受控。
2. 父块承担上下文补全，子块承担精确命中。先检索子块，按命中情况补充父块或相邻段落；对父级标题、事件概括建立可搜索入口。并非把每个父块都向量化，也不是命中子块就整章全发。
3. 保留原文片段作为证据，摘要作为定位线索。旧的五章合并可继续兼容，但不能替代原子事实和原文证据；不再对旧摘要反复压缩后当作唯一事实来源。
4. 混合召回采用浏览器本地关键词检索与外部向量检索并行。关键词检索覆盖中文、人名、别名、物品名与精确短语；向量覆盖同义改写。可借鉴 BM25 的词项评分，但不能直接采用只适合英文空格分词的默认方式。
5. 两路候选采用基于排名的融合，例如 RRF，避免直接相加量纲不同的分数。合并重复片段、按书籍和分支过滤，再重排，最后按第 1 项预算选择。
6. 基础重排在本地结合专名、人物、事件、时序和目标章关联；可选外部 rerank API 提高语义判断。只有支持且用户启用时才调用；不把整本书交给模型重排。未启用外部重排时如实显示采用本地排序。
7. 在现有连接中心复用配置和凭据管理，明确向量模型与重排模型的用途、连接、测试结果和状态。请求遵循现有适配入口，验证跨域、认证、超时、返回数量、维度与有限数值；不静默回退到别的账号或模型。
8. 索引采用分批、可暂停、可取消和变化块重建。服务商、模型或维度变化后标记不兼容，不能混算不同向量；进度、失败批次和额外请求数量可见。
9. 向量或重排失败时保留原有记忆，回退到本地关键词检索和基础排序，明确降级原因，不把无结果伪装为“没有相关事实”。打开书、输入和查看设置不自动触发整书重建。

### 验收

1. 建立固定问题集，至少包含人物专名、别名、同义改写、早期伏笔、物品归属、状态变化、秘密知情人与跨卷事件；每个问题预先标注正确章节和事实。比较旧方案、纯关键词、纯向量和混合重排结果。
2. 分别记录候选命中、重排后命中、预算裁剪后实际发送命中，防止“检索到了但最终没发”。在同一总预算下，关键必测事实应进入最终请求；一般问题报告召回率和错误来源，不仅展示成功示例。
3. 子块命中后能追溯父块和原文，补充必要的因果、代词指向与知情范围；重复父块只发送一次，不因命中多段而重复塞整章。
4. 错误书籍、分支独有事件、目标章之后的情节不得进入候选或请求。缺省故事时间与存在显式故事时间两种情况都要测试。
5. 本地 mock 覆盖 API 超时、429、认证错误、数量不符、空向量、维度变化、取消与切书；验证索引不损坏、旧记忆保留、降级可见。
6. 另用实际选择的向量服务、可选重排服务验证真实请求和返回；报告服务商、模型、适配方式、批量限制和跨域结果。未完成真实服务验证时，不宣称该服务商兼容。
7. 记录索引首次构建与增量更新的请求数、耗时和数据量；改一处正文只更新受影响块，不重新调用全书向量 API。

## 3. 旧记忆关联、修改后的有效性与迁移

### 问题

1. 当前有效性检查同时依赖章节 ID、分支和正文指纹。只改一个错字也会让原记忆不再被当作有效内容使用，缺乏足够清楚的状态提示。
2. 历史真实备份中保留了 205 条找不到现存对应章节的记忆。现有材料能证明它们未能关联，不能证明全部由改错字造成，也不能保证每条都能自动恢复。
3. 旧格式、导入后 ID 重映射、分支继承、正文重生成和章节删除会产生不同原因的关联问题，不能统一当成内容已经失效后直接丢弃。

### 要求

1. 以稳定的书籍、分支、章节和块 ID 维护身份关系，以内容版本判断是否需要更新；内容指纹用于比较变化，不作为唯一关联身份。
2. 区分可用、待更新、已禁用、来源缺失、处理中和失败状态。正文变化后保留旧记录及原来源，不再无声过滤；是否继续参与请求取决于变化性质和来源证据，不能把可能过时的事实无条件当真。
3. 优先复用未变化的块。能确认只是空白、标点等无事实变化时允许复用；涉及人名、否定、数值、物品归属或事件变化时，相关块及依赖父块标记待更新。不能用“编辑距离很小”直接认定安全。
4. 新记录生成、校验和保存成功后再替换旧记录；失败或停止保留旧记录。请求期间切书、切分支或继续编辑时，迟到结果不得覆盖新内容。
5. 旧记忆迁移先使用可靠 ID、导入映射、已保存来源与章节证据关联。相似度只能提出候选；多义或证据不足的记录交用户核对，保留“未关联记忆”入口，不按章号强行配对。
6. 迁移报告记录总量、成功关联、待更新、未关联、禁用和失败数量。保留迁移前数据与版本信息，支持撤销本轮迁移和重新尝试。

### 验收

1. 以同一章分别修改错字、标点、人物名、否定词和数值，核对状态变化、保留的旧记录、受影响块和最终请求；不得出现一字变化后整章记忆静默消失。
2. 覆盖章节改名、重排、删除、正文重生成、主支线分叉、跨书导入与 ID 重映射，确认记录不串书、不串分支、不把旧事实覆盖新事实。
3. 在可使用的真实旧备份中核对 205 条记录的数量去向；能关联的给出证据，不能关联的完整保留，不承诺无依据的全部自动恢复。真实书稿不进入公开报告或外部检索。
4. 补录失败、取消、保存失败和切书期间，旧记忆仍在；刷新及全量导出再导入后状态和来源关系保留。
5. 对已无原文章节的记忆，界面和请求均能区分来源缺失与来源确认；用户未处理前不得默认为已核实事实。

## 4. 召回注入位置、排序与实际请求一致性

### 问题

1. 当前增强召回寻找最后一条 `user` 消息并追加文字。消息顺序变化时，可能落到生图提示词等用途不同的消息里；是否正好命中该消息取决于具体构造路径，不能只凭消息角色判断写作用途。
2. 当前代码先按相似度取前若干条，再按章节顺序重排。最终排列丢失了检索相关度顺序，较相关的事实未必优先占据预算和位置。
3. 安全预览、检索列表和最终服务商请求可能处于不同组装阶段，仅看到召回结果不能证明写作模型实际使用了对应材料。

### 要求

1. 以明确的上下文用途或槽位定位“已发生事实参考区”，不再依赖“最后一条 user 消息”。正文续写、重生成、中断续写及已经接入的写作建议等入口复用同一组织结果。
2. 召回材料与当前作者要求、生图指令、系统规则分开组织，带来源、时间范围和事实性质说明。材料中的命令、引号或角色台词只作为素材，不能升级为指令。
3. 先依相关度和明确优先级选择，再对同一事件内部按时间组织；需要交代因果时局部排序，不把全体候选重新排成章号顺序。
4. 父块、子块、近期正文、摘要和角色事实统一去重并计入第 1 项预算。尊重作者手工设定；发生冲突时保留来源和冲突状态，不自动改写角色档案。
5. 在各服务商适配前形成一份本次上下文结果，再派生预览、说明和最终消息；在适配后的实际请求上校验内容没有被挪错、重复或删除。
6. 增加可读的召回说明：命中来源、关联章节、排序原因、实际发送与未发送原因、是否使用外部 API。普通界面不暴露密钥或无关内部提示词。

### 验收

1. 构造最后一条 user 消息含生图指令的场景，核对召回仍进入写作事实区，生图指令未被混入；关闭生图后同样成立。
2. 用第 1 章高度相关、第 80 章弱相关的样例证明最终选择遵守相关度，而不是默认近期或章序优先；时间补全只发生在相关事件内部。
3. 拦截正文生成、重生成和中断续写的请求；对项目支持的 OpenAI 兼容与 Gemini 等实际适配方式逐项检查，覆盖相关功能开关组合。仅本地 mock 通过与真实服务商通过分别报告。
4. 预览里的“实际发送”条目、来源和预算与请求体一致；重复段落不重复计入，未关联旧记忆和未来情节不混入。
5. 用含“忽略前面规则”等文本的原文片段验证其仅被标为参考材料；不以提示词存在就宣称真实模型绝对不会受影响，真实生成结果另作人工抽查。

## 5. 大对象存储、向量与重生成快照

### 问题

1. 当前 `DB.saveLibrary` 把完整书库写到同一条 `library_v6` 记录。正常 IndexedDB 路径保存的是对象，并非每次都先生成一个 JSON；但仍需处理完整对象，备用路径与关页路径还会整库 JSON 序列化。
2. 保存快照同时包含当前书的顶层字段及 `books` 内的同书数据，存在重复表达；记忆、向量、正文和重生成请求一起扩大保存成本。
3. 历史真实备份约 200.7 MB，其中重生成请求快照约 185.2 MB。之前提供手动清理只处理已有体积，没有改变之后持续积累与反复保存的成本。
4. 独立的本机书籍恢复点与随章节保存的重生成请求不是同一类数据。现有全量书籍备份并未包含全部独立恢复点，需要明确备份边界。

### 要求

1. 保留 `DB.saveLibrary` 作为公共入口、原数据库名称与书籍逻辑归属。优先评估在原 IndexedDB 中分记录保存书籍、变化章节和大附件式快照，外部使用方式仍为单页网页。
2. 向量和索引继续属于对应书籍，但作为可重建数据分开管理；普通文本修改不重复写入未变化向量。重生成请求等大内容按需保存和读取，不与每次小编辑捆绑重写。
3. 用稳定引用和内容去重减少首次请求中的重复上下文，同时保证“复用首次注入”能恢复相同请求材料；不能只删除字段、截短内容后仍声称完整保留。
4. 旧顶层兼容字段在读取和导出边界处理，减少新库内部重复持久化。单书、全量、分支备份保持可导回，凭据仍与普通书籍导出分离。
5. 新布局的内容写入与索引更新需在事务内保持一致；先写好新数据再切换读取标记，不先删旧库。迁移失败、空间不足或中断时仍能读取原存档。
6. 明确旧版程序如何读取迁移后的内容：保留必要旧数据或提供兼容导出及恢复办法。回滚位置必须包含数据恢复方法，不能只有代码提交号。
7. 首次请求快照保留现有查看和手动清理能力；支持按需选择是否保留后续快照，先说明会影响什么。不得以优化性能为由自动删除旧稿、作者记忆或用户未同意清理的历史。
8. 在备份界面明确独立恢复点是否包含在本次导出；本轮至少让备份范围与实际一致。若纳入完整备份，须覆盖导入、数量、引用与旧格式兼容。
9. 不引入新的创作数据 localStorage 键。确需改变 IndexedDB 布局或审计基线时，列明新增范围、理由和兼容办法；开工前若与现行项目规则实质冲突，单独确认。

### 验收

1. 记录数据库实际写入的键、记录数与数据量，证明修改一章不会重写别书、全部向量和所有旧快照；仅减小保存次数不算完成本项。
2. 以旧库、旧单书 JSON、旧全量 JSON 和多分支备份升级，再保存、刷新、导出、导回，核对正文、旧稿、角色、规划、记忆、来源、向量和快照数量及内容指纹。
3. 首次注入复用前后比较消息内容、顺序和选项；去重或拆分不改变其原始材料。删除快照仍不删除章节正文或正文旧稿。
4. 在迁移中断、事务失败和配额不足场景下验证原数据仍可恢复，新库不会留下指向缺失内容的索引。旧版恢复办法实际走通。
5. 全量备份明确列出包含与不包含的数据。未包含独立书籍恢复点时必须如实提示，不得用“全量”暗示所有历史都已打包。

## 6. 角色分类：正派、反派、其他 NPC

### 问题

角色数量增加后，现有列表难以快速找到目标。项目已有势力或阵营资料，但“属于哪个组织”和“正派、反派、其他 NPC”是两个维度，不能拿现有势力名称直接替代本次分类。

### 要求

1. 在角色档案增加单选分类：正派、反派、其他 NPC；提供“全部”筛选，并显示各类数量。分类只表达作者的整理方式，不要求 AI 评判人物善恶。
2. 旧角色未填写时归入其他 NPC，保留原势力、关系、身份与描述，不根据名字或正文自动猜测分类。已有明确字段若可可靠映射，先核实语义再迁移。
3. 支持单个角色修改和第 7 项的批量修改。分类与名称搜索、原有势力筛选可以组合，切换筛选不清空角色数据。
4. 分类作为角色资料随原书保存、备份和导入；同一角色仅保存一份字段，避免各入口维护不同分类。现有分支角色状态沿用原有范围，本次分类不额外创造另一套分支存储。
5. 复用角色工作台现有布局和筛选组件；移动端可完整选择和操作，不能因增加一列将角色卡挤窄。

### 验收

1. 用至少 100 个角色、同名角色、超长名称和未分类旧角色验证三类计数、筛选与搜索组合；角色数量总和正确，身份以稳定 ID 区分。
2. 修改分类后保存、切书、刷新、导出再导入，分类保留，其他书籍和原势力资料不受影响。
3. 320/360 手机、768 断点、1024 触屏平板和 1280 电脑明暗主题检查实际点击与布局；空白角色、超长无空格文本下卡片不被挤成窄条。

## 7. 角色批量修改

### 问题

境界、力量等级和其他常用角色状态需要重复维护，目前逐个打开修改效率低。一次性覆盖过多字段又容易误伤已有内容，需要明确选择范围、改动字段与空值含义。

### 要求

1. 在现有角色列表提供多选、当前筛选结果全选、取消选择和已选数量。全选明确指当前结果，不把隐藏的其他分类角色自动算进去；筛选变化时已选数量和对象可核对。
2. 第一批支持分类、现有境界／等级、力量等级，以及现有角色结构中可复用的身份、状态、标签、势力等常用字段。以当前档案实际字段为准，不为同一概念新增重复字段。
3. 字段以可复用配置驱动，共用单角色字段校验和保存逻辑。自定义等级体系保留原名，不能强行把“筑基”换算成数字，或假设不同角色的等级可直接比较。
4. 默认只修改用户勾选的字段；未选择表示保持原值。明确区分“保持”“设为某值”和“清空”；标签等列表支持替换、追加、移除，并去重。第一版不加入自动猜测等级或任意文本脚本批量执行。
5. 确认前预览角色、旧值、新值与冲突。多角色原值不同时显示“多个值”，不能误显示第一人的值后覆盖全部。无实际变化时不触发整批保存。
6. 应用前核对原书籍与角色是否仍存在，操作期间切书或对象变化时停止过期应用。保存失败时恢复整批旧值，不出现一部分显示已改、一部分未保存。
7. 提供最近一次批量修改撤销，按实际旧值逐个恢复；发现用户已再次编辑时提示冲突，不用旧撤销直接覆盖后续修改。批量修改后对相关摘要或索引做定向失效处理，不重建全书。
8. 共用原保存队列，一批操作合并落盘；不为每个角色分别触发整库保存。

### 验收

1. 同时选择不同分类、不同原等级及同名角色，只修改等级，确认姓名、关系、提示词、其他状态和未选角色完全不变。
2. 验证当前筛选全选、跨筛选保留选择、清空选择、0 人选择、已选角色被删除和操作期间切书；预览数量与最终改动 ID 一致。
3. 验证保持、清空、设值，标签追加／移除／替换与重复项处理；无变化批次没有额外写入。
4. 一次保存完成后刷新和备份导回，所有改动保留；强制保存失败时整批回滚。最近一次撤销按角色原值恢复，后续手工修改不会被静默覆盖。
5. 至少覆盖 100 个角色的批量预览和应用，记录保存次数及响应时间，并在手机与触屏平板完成实际点选和确认。

## 8. 加载、编辑、切书与关闭卡顿

### 问题

1. “每一次操作都读取整库”不准确。普通输入有两秒防抖，正常保存先读取小的修订号；但每次真正保存仍会整理并写入完整书库，多处关键节点会立即保存。
2. 启动读取整库，载入书籍会深拷贝全部章节和其中的大快照，再逐章处理。实际切书还包含旧书同步、新书载入和立即保存，不能把 `loadBook` 单函数耗时当作整步切书耗时。
3. 关闭处理先调用 `syncBookData`，随后调用内部也会同步的 `buildLibrarySnapshot`，存在重复工作；之后同步 `JSON.stringify` 整库，最后才发起异步 IndexedDB 写入。即使没有新的内容修改也会经过该处理。
4. 已有记忆监听同步遍历可见章节。未变章节有指纹缓存，不能声称每次都重新计算全书全文；但遍历、变化章节的计算、渲染和其他同步工作仍需分别测量。
5. 隔离浏览器实测已证明数据量增大时保存和关页处理明显变慢，但尚未完成真实反馈书库的完整分段归因，不能说全部延迟都来自同一个函数。

本轮已有实测：本机已有 Edge，通过 CDP 使用临时档案和合成书籍；没有使用日常书库，也未调用外部 AI API。下表单位为毫秒，快照体积指合成请求快照文本规模，不是完整持久化记录大小。

| 合成输入 | `loadBook` 调用 | 快照组装 | 一次保存总耗时 | 其中 IndexedDB 写入 | 关页同步处理 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2 章，约 64 KB 快照文本 | 6 | 4 | 54 | 5 | 7 |
| 24 章，约 24 MiB 快照文本 | 76 | 7 | 189 | 110 | 340 |

这组结果用于确认大对象处理的成本会增长，不是最终性能基线：不是多次测量的 P95，不代表真实 200 MB 书库，也不等于浏览器完全退出耗时。曾观察到长任务，但尚未单独隔离归因，不能据此声称某函数阻塞超过一秒。后续正式比较须重新记录窗口、设备、开关和样本次数。

### 要求

1. 将本项与第 5 项一并实施，核心目标是减少每次操作处理的数据范围，而不只是把两秒防抖改得更长。
2. 先分段测量启动读取、解析、迁移、载入、渲染和首次可操作时间；切书区分旧书同步、新书复制、重算、渲染及保存。分清网络下载慢、数据库慢和页面计算慢。
3. 普通编辑只标记和保存变化内容，合并重复保存及同步，避免未变化的大快照和向量参与每次遍历。只有变化范围需要修复引用或更新指纹，不在每次普通保存里完整重复检查。
4. 重生成请求、历史详情和非当前书大内容按需读取；长章节列表与角色批量预览若有渲染瓶颈，依据实测采用分段显示或窗口化，不先引入大型组件库。
5. 索引、切块、指纹等计算尽量处理变化部分；确需大批处理时分批让出页面执行时间，必要时再使用浏览器 Worker。用户输入、滚动和点击优先，关闭记忆付费维护后不继续做无关全书计算。
6. 关闭前只处理未保存的变化与必要草稿，移除重复整库同步和整库同步 JSON 转换。正常编辑期间及时完成持久化，不把保存安全全部押在关页异步请求上。
7. 保留保存失败、空间不足、多标签冲突、生成中中断草稿和应急恢复的真实能力；减少同步处理不能以丢稿、吞掉保存失败或取消保护为代价。
8. 对大书性能建立固定样例和基线。参考环境、数据、次数和统计方式开工前锁定；实施后不能换更小样例、减少正文显示或降低断言来宣称变快。

### 验收

1. 参考电脑用本地 HTTP 页面和隔离浏览器，覆盖小书、多书、百万字正文、大量向量、24 MiB 快照和约 200 MB 级备份；真实备份仅在本机有可用材料时测试，不把同体积合成数据当作真实备份。
2. 每个固定操作重复测量，记录中位数、P95、主线程长任务和写入范围。分别测启动首次可操作、输入至下一次显示、设置开关、切书、普通防抖保存、立即保存、关页处理与实际离开页面。
3. 性能目标：普通编辑不重写其他书或未变化的大快照；参考电脑同样例输入响应 P95 目标不高于 100 ms；关页无待保存内容时不做整库处理。大样例启动和切书目标较旧版中位数至少降低 30%，同时小书不得出现可重复的明显退步。数值为本轮拟定验收目标，尚非已取得结果；移动端另记实测，不冒充参考电脑结果。
4. 用请求与数据库记录证明打开设置、滚动和无内容变化的关闭没有触发向量重建或重复整库写入。后台索引开启时仍可输入、滚动和停止任务。
5. 输入后立即刷新、编辑早期章节后关闭、生成中关闭、连续切书、保存进行中继续编辑与多标签冲突均检查最新内容。分别报告正常关页、浏览器崩溃模拟和真实系统强退的覆盖范围，不能把模拟结果当作真实断电保证。
6. 电脑、手机尺寸和触屏平板在相同书籍下复验；窗口缩小、软键盘模拟、明暗主题与恢复电脑后，按钮可见、点击有效、正文末段可达。
7. 最终报告逐项列出改善与剩余慢点。如果主要等待仍来自网络或首次重建，明确归因，不使用加载动画掩盖等待。

## 实施顺序与共同验收

1. 固定稳定基线和大书样例，记录现状性能与备份指纹，保护原有未提交内容。先明确第 5 项存储布局的兼容与回滚范围。
2. 先处理第 5、8 项的基础保存和读取成本，为新记忆索引提供增量保存能力；避免新记忆系统建立在旧整库瓶颈上。
3. 处理第 3 项旧记忆来源与版本，再落实第 1 项预算、第 2 项检索和第 4 项注入；按同一组固定问题与最终请求验证整条链路。
4. 复用现有角色资料完成第 6、7 项，同步验证保存次数和长列表性能。
5. 审查并清理本轮废弃或重复代码，重新执行受影响的语法、结构与功能检查。单文件模板改动必须通过 `npm run audit`；发布前执行 `npm run gate`、`npm run gate:browser`，再运行本轮新增专项。失败或跳过都不得表述为全部通过。
6. 本地验收覆盖 320/360 手机、768 断点、1024 触屏平板、1280 电脑、横屏与明暗主题。新控件点击高度至少 44 px；角色卡检查实际父子层级、宽度、命中与长文本，不只检查横向溢出。
7. 交付检测报告与更新说明，写明命令、协议、尺寸、开关、模型、样例、机器证据、原始失败、未覆盖范围、代码及数据回滚位置。mock、浏览器回归、真实服务商与真机验证分别报告。
8. 获准上传后仅发布公测候选，核对账号、仓库、候选 SHA、Pages 来源、构建状态和线上字节，再执行 `npm run gate:release -- --site public` 及本轮公测专项。正式库不接收本轮候选；公告日期在获准上线当天按指令处理。
